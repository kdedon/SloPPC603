# MPC602 standalone floating-point contract

This contract defines the **compile-time 602 personality** of the standalone FPU. The default 603e personality remains governed by [FPU_CONTRACT.md](FPU_CONTRACT.md). `602 UM` is Motorola/IBM, *PowerPC 602 RISC Microprocessor User's Manual*, MPC602UM/AD / MPR602UMU-01, 11/95: [pinned scan](https://zxgit.org/RomanRom2/awesome-cpus/raw/commit/8115b6c97d547c13037b0cfcb0125d09a3e90543/PowerPC/PowerPC_602/manual.pdf), SHA-256 `77c0fc4a7c4f0cbec82940d45e4dca0186404b46fbb431ce247818af05e6b1e3`. `PEM` is the local *Programming Environments Manual*, `MPCFPE.pdf`. Page numbers below are **one-based physical PDF pages**; printed chapter pages follow where useful. This is a source contract and implementation gate, not a claim that the present 603e RTL already implements 602 behavior. [602 UM title, PDF 1; §§1.2.2.2, 2.3.4.2, PDF 56, 116–122]

## Register and tag model

The PowerPC UISA defines 32 architectural 64-bit FPRs, but the 602 implements 32 **32-bit hardware FPRs**. Emulation software maintains the architected 64-bit image for double values that cannot live in the hardware file. Four FPR rename registers forward pending results. A valid hardware binary32 value has its `SP` tag set; a hardware integer has its `LT` tag set. When both tags are clear, the architected value resides in the software-managed double image. SP and LT are independently writable: an instruction tests the tag it requires, and the manual prescribes no extra trap solely because both bits are set. [602 UM §§1.2.2.2, 2.1.2.4.1, 6.4.3, PDF 56, 97, 304–305 / 1-20, 2-21, 6-16–17]

`SP` and `LT` are 32-bit supervisor-level SPRs 1021 and 1022. Bit `n` denotes FPR `n` in architectural bit numbering; software reads/writes them with privileged `mfspr`/`mtspr`. Table 2-6 accidentally prints SP as `102`, but its encoding `11111 11101` and §2.1.2.4.1 identify **1021**. Power-on reset does **not** clear either register; startup software must initialize both. A standalone implementation may use deterministic simulation reset values but must not report them as silicon power-on values. Tag and raw-FPR changes from an instruction commit atomically; a trap, abort, or killed instruction changes neither. [602 UM §§1.2.2.7, 2.1.2, Table 2-6, 2.1.2.4.1, 4.5.18, PDF 59, 87, 97, 221 / 1-23, 2-11, 2-21, 4-39]

`lfs` leaves binary32 bits in the hardware FPR instead of widening them to binary64. `fctiwz` and `mffs` leave a 32-bit integer/FPSCR word in the hardware FPR with `SP=0, LT=1`; `fctiw` is not a hardware operation. An `SP=0` arithmetic source does not silently use a zero-filled 64-bit view: it takes an emulation trap. [602 UM §§2.1.3, 2.2.1, 2.3.4.2.7, Tables 2-26, 2-28, 2-35, PDF 101–103, 120–121, 127–128 / 2-25–27, 2-44–45, 2-51–52]

## Instruction disposition

Decode uses the same primary/XO encodings and reserved-field legality checks as the 603e contract; the 602 changes **execution disposition**. The rows below cover every floating-point class the 602 manual lists. An emulation trap has vector offset `0x1600`; it is distinct from illegal-instruction program exception `0x0700` and FP-unavailable `0x0800`. A trap result never writes FPR, tags, FPSCR, CR, or an update-form base register. [602 UM §§2.3.4.2–3, 4.5.7.2, 4.5.8, 4.5.18, Tables 6-5–6, PDF 116–129, 212, 221, 315–318]

| --- | --- | --- |
| `fadds`, `fsubs`, `fmuls`, `fdivs` | Every source has `SP=1`; result is binary32 in frD, `SP=1, LT=0`. Missing source SP traps. | 602 UM §§2.2.1, 2.3.4.2.5, Table 2-24, PDF 102–103, 118–119 |
| `fmadds`, `fmsubs`, `fnmadds`, `fnmsubs` | All three sources require SP. The multiply-add has one final rounding, retaining the full 48-bit single product fraction before add/subtract. Result SP=1, LT=0; missing SP traps. | 602 UM §2.3.4.2.6, Table 2-25, PDF 119–120 |
| `fadd`, `fsub`, `fmul`, `fdiv`, `fmadd`, `fmsub`, `fnmadd`, `fnmsub` | Double-result arithmetic always traps for software emulation, even if source values happen to fit binary32. | 602 UM §§2.2.1, 2.3.4.2.5–6, Tables 2-24–25, PDF 102–103, 118–120 |
| `fres` | Requires an SP source; executes as an **exact, rounded single-precision divide**, not as the 603e reciprocal estimate. Result SP=1, LT=0. It blocks the FPU for 18 cycles. | 602 UM §2.3.4.2.5, Table 2-24, §6.4.4, Table 6-5, PDF 119, 305, 315 |
| `frsqrte` | SP source required. Estimated reciprocal square root is within one part in 32; hardware target is binary32, SP=1, LT=0. Missing SP traps. The manual gives an accuracy bound, not exact table bits. | 602 UM §2.3.4.2.5, Table 2-24, Table 6-5, PDF 119, 315 |

| `frsp` | A finite normal SP source is copied as a 32-bit value, with destination SP=1, LT=0. An emulated double or integer source traps. Signaling NaN still follows Table 2-23's invalid/quieting rule for a round-to-single instruction; a denormal source can invoke the underflow behavior below. | 602 UM §2.3.4.2.1, Table 2-23, §2.3.4.2.7, Table 2-26, PDF 116–117, 120–121 |

| `fmr`, `fneg`, `fabs`, `fnabs` | Source SP required; copy or change binary32 sign bits, set destination SP=1, LT=0. These moves do not change FPSCR; Rc copies CR1 from FPSCR. | 602 UM §2.3.4.2.10, Table 2-29, PDF 122 |

All update-form FP memory instructions retain the PowerPC prohibition on `rA=0`. Stores require side-effect-free translation, protection and alignment preparation; neither a trap nor a fault may publish a store or base update. The 602 supports some misaligned memory operations but specifically lacks hardware support for a floating-point **store** that is not word-aligned, so that access takes alignment exception. [602 UM §§2.2.3, 2.3.4.3.8–9, PDF 104, 127–129 / 2-28, 2-51–53]

## FPSCR, numerical exceptions, and MSR

The FPSCR has the PowerPC bit layout and RN, enable, sticky, FX/FEX/VX, FR/FI/FPRF semantics defined by PEM and detailed in [FPU_CONTRACT.md](FPU_CONTRACT.md). The 602 manual states it implements the architectural FPSCR. Numeric operations retain PPC NaN selection, signed-zero and one-round fused semantics where the 602 manual does not override them. A binary32 hardware result remains **binary32 bits** in the 602 hardware FPR; a binary64 FPR encoding would be the wrong storage representation. [602 UM §§1.2.2.4, 2.2.1, 2.3.4.2, 4.5.7.1, PDF 56, 102–103, 116–122, 211–212; PEM §§2.1.3–4, 3.3, PDF 68–72, 123–150]

With `FPSCR[NI]=0`, source denormals are accepted, but **any underflow condition**, including an exact tiny result for which IEEE UX can remain clear, traps to `0x1600` for software completion when UE is disabled. When an FPSCR exception enable is set for a generated numeric condition, §4.5.7.1 requires an emulation trap **regardless of MSR FE**, without an FPR or FPSCR update. Thus enabled underflow traps too. With `NI=1`, hardware delivers signed zero on underflow, judged before final rounding; a tiny nonzero intermediate that would round up to minimum normal still takes the zero result. Divide by zero, invalid, and overflow produce the listed default results, subject to the enabled-exception trap taking priority over an architectural write. NI does not disable exception detection. A NaN input yields a quiet NaN; the 602 manual does not fix its exact payload bits. [602 UM §§2.3.4.2.1–4, Table 2-23, 4.5.7.1, PDF 116–118, 211–212 / 2-40–42, 4-29–30]

Table 2-23 fixes the NI=1 **delivered value** but does not give a complete FR/FI/UX/XX transition table for an exact tiny value forced to zero or for a tiny value that otherwise rounds up to minimum normal. The current implementation policy retains the IEEE pre-flush exception metadata and overrides the delivered bits with signed zero; that policy is tested, but it is not claimed as a proven silicon-exact status rule. This remains a bounded semantics gap. [602 UM §§2.3.4.2.1–4, Table 2-23, PDF 116–118; PEM §3.3.6.1.2, PDF 143–145]

`MSR[FP]=0` gives FP-unavailable `0x0800` for a valid floating-point instruction, including FP memory and moves, unless a higher-priority exception exists. The 602 handles all FP exceptions precisely. Its FE0≠FE1 imprecise settings behave as precise for this implementation. The manual's `MSR[NI]` phrase in this context is a typo for FPSCR[NI]; NI is not an MSR bit. The core supplies MSR controls and chooses the final exception vector/prefix; the standalone FPU reports disposition. [602 UM §§4.5.7–8, PDF 211–212 / 4-29–30; Table 4-2, PDF 186–188]

There is a source tension: Table 4-2 describes an enabled `FPSCR[FEX]` program exception when FE is active, including when a move-to-FPSCR instruction sets an enabled condition, while §4.5.7.1 explicitly sends **numeric** enabled exceptions to the 602 emulation handler independent of FE. Apply the specific emulation rule to numeric instructions and the Table 4-2 program-exception rule to FPSCR control writes. Do not silently reuse the 603e rule for 602 arithmetic. The 603e manual reproduces the 602 emulation language despite its own vector table reserving `0x1600`; this strongly suggests copied text but is an inference, not a published erratum. [602 UM Table 4-2, §§4.5.7.1, 4.5.18, PDF 186–188, 211–212, 221; 603e UM Table 4-1 and §§4.5.7.1, PDF 162–163, 188]

## Timing and standalone interface gate

The 602's hardware FPU has a three-stage pipeline, up to three simultaneous FP instructions, four FPR rename registers, and a **four-entry** in-order completion FIFO. Most supported arithmetic, compares, moves and `frsqrte` have `1-1-1` stage timing and **one instruction per cycle initiation**. `fdivs` and `fres` take 18 cycles and block the FPU. `mffs`, `mtfsb0`, `mtfsb1`, `mtfsfi`, `mtfsf` also block the FPU until completion. A newly changed disabled exception sticky bit may add one or two **completion serialization** cycles; it is not a fixed execute-stage penalty. These are target timing behaviors; a serialized one-in-flight shell is incomplete for 602. [602 UM §§1.1.3.1.3, 1.2.2.2, 4.5.7.1, 6.3.2, 6.4.3–4, Table 6-5, PDF 45, 56, 211, 299, 304–305, 315–316]

LSU timing, including memory transport, is `2:1` latency:throughput for `lfs`, `stfs`, `stfiwx` and `3:2` for `lfd`, `stfd` under the table's assumptions. The external LSU boundary must preserve atomic 64-bit operand checks and all fault/commit effects; the standalone FPU cannot claim full core-level cache timing without that LSU. [602 UM §6.8.5, Table 6-6, PDF 316–318]

Select the personality at elaboration with `parameter bit CPU_602`, default false. There is no runtime personality input. In 602 elaboration, physical FPR storage is 32 bits per entry plus SP/LT tag state; status and arithmetic use the selected 602 rules. The tagged issue/result/commit/abort/kill protocol remains; the result packet needs an explicit `0x1600` emulation-trap kind, and exact-tag commit must be the only state-write point. The 602 SP/LT SPR accesses need an integration-visible path or decoded FPU issue handling. Pipelined implementation must retain exact completion identity, source forwarding, in-order FPSCR/CR1 effects, and branch-visible compare timing. [602 UM §§1.2.2.2, 2.1.2.4.1, 4.5.18, 6.4.3–4, PDF 56, 97, 221, 304–305]

The 602 acceptance matrix needs, in both compile-time personalities: binary32 raw register/tag transitions; all source-tag trap cases including unselected `fsel`; exact `fres` against an independent binary32 divide oracle; `frsqrte` accuracy and SP output; `lfd` exact-fit boundary and NaN/inf/denormal traps; `stfd` expansion and rejection; `stfiwx` LT gate; `mffs`/`mtfsf` LT behavior; NI/IEEE underflow, VE/ZE/OE/UE trap suppression and status-control exception tests; MSR FP/FE behavior; kill/abort/commit-only effects; and directed 3-stage initiation / divide-blocking timing. [602 UM §§2.1.2.4.1, 2.3.4.2–3, 4.5.7–8, 6.4.4, Tables 6-5–6, PDF 97, 116–129, 211–212, 305, 315–318]
